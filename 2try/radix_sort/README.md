# Параллельная реализация алгоритма цифровой сортировки (radix sort, `uint16_t`, C++17 + OpenMP)

Курсовая работа. Консольное приложение `sort_app` сортирует массивы 16-битных беззнаковых
целых (`std::uint16_t`, значения `0..65535`, до 10⁹ элементов) двумя способами —
последовательно и параллельно на OpenMP — и **честно сравнивает** их производительность.

## 1. Краткое описание

Ключ занимает ровно 16 бит, то есть это одна «цифра» с основанием `K = 2¹⁶ = 65536`.
Цифровая сортировка по такому ключу вырождается в **один проход** — сортировку подсчётом
(counting sort) с асимптотикой `O(N + K)`.

| Что | Где |
|---|---|
| `serial_radix_sort` — последовательный стабильный эталон | `src/radix_sort.cpp` |
| `parallel_radix_sort` — OpenMP: локальные гистограммы + глобальные префиксные суммы + непересекающиеся диапазоны записи | `src/radix_sort.cpp` |
| `ParallelRadixWorkspace` — рабочая область, создаётся один раз и переиспользуется | `src/radix_sort.hpp` |
| Расширение `fill` (необязательное): «гистограмма + заливка диапазонов», на месте | `src/radix_sort.cpp` |
| Быстрый ввод-вывод (текст и бинарный формат), генератор, проверка корректности, бенчмарк | `src/io.*`, `src/data_gen.*`, `src/verify.*`, `src/benchmark.*` |
| Предварительная проверка «хватит ли ОЗУ» (защита от многочасового swap), журнал прогресса | `src/sysinfo.*`, `src/main.cpp` |
| Тесты, необязательный Google Benchmark | `tests/`, `bench/` |

```text
radix_sort/
├── CMakeLists.txt
├── README.md
├── src/
│   ├── main.cpp            CLI: режимы serial / parallel / benchmark / generate
│   ├── radix_sort.hpp/cpp  алгоритмы, ParallelRadixWorkspace, оценка памяти
│   ├── io.hpp/cpp          буферизованное чтение/запись (text, binary)
│   ├── data_gen.hpp/cpp    детерминированный генератор данных
```

## 2. Последовательный алгоритм

1. **Подсчёт.** `count[v]` — сколько раз значение `v` встретилось во входе.
2. **Префиксные суммы.** `start[v]` — *exclusive prefix sum*: сколько элементов строго меньше `v`
   (`start[0] = 0`, `start[K] = N`).
3. **Стабильная запись.** Выходной буфер того же размера; вход обходится **с конца**
   (`for (i = N; i > 0; --i)`), каждый элемент ставится на предпоследнюю свободную позицию
   диапазона своего значения. Последний из равных ключей оказывается последним — порядок сохранён.
   После этого `data` и `buffer` меняются местами за O(1), копирования массива нет.

Реализация использует **одну** таблицу `bound[0..K]` вместо пары `count`/`start`: счётчики
накапливаются в сдвинутую ячейку `bound[x+1]`, обычная накопленная сумма даёт ровно
`bound[v] = start[v]`, а `bound[v+1]` служит убывающим курсором значения `v`. Горячая таблица
занимает 256 КиБ вместо 512 КиБ, поэтому эталон не «искусственно медленный» и ускорение
не завышается слабой базой сравнения.

## 3. Параллельный алгоритм

Пусть `T` — число потоков OpenMP. Вход делится на `T` **непрерывных блоков по числу элементов**
(размеры отличаются не более чем на 1). Поток `t` владеет блоком `t` и собственной
гистограммой `local[t][0..K)`.

```text
INPUT
  │  разбиение на T блоков (по числу элементов)
  ▼
Фаза 1  каждый поток: локальная гистограмма своего блока       (без синхронизации)
  │  ───────────────────────── барьер ─────────────────────────
  ▼
Фаза 2  global[v] = Σ_t local[t][v]                            (потоки делят значения: K/T на поток)
        start[v]  = Σ_{u<v} global[u]                           (двухуровневый префикс)
        local[t][v] ← start[v] + Σ_{t'<t} local[t'][v]          (стартовая позиция записи)
  │  ───────────────────────── барьер ─────────────────────────
  ▼
Фаза 3  каждый поток: for x in свой блок (слева направо):
            out[ local[t][x]++ ] = x                            (только в свои диапазоны)
  ▼
OUTPUT   (неявный барьер конца параллельной области; затем swap(data, buffer))
```

**Диапазоны потоков.** Для значения `v` отрезок `[start[v], start[v+1])` нарезается подряд
на куски длиной `local[0][v], local[1][v], …, local[T-1][v]` — строго в порядке номеров потоков.
Пример из ТЗ (`v = X`, всего 14 элементов, по потокам 5/3/2/4):
`[s, s+5)`, `[s+5, s+8)`, `[s+8, s+10)`, `[s+10, s+14)`.

**Нет перекрытий.** Куски не пересекаются и покрывают отрезок без дыр. Поток `t` при записи
увеличивает курсор значения `v` ровно `local[t][v]` раз (он обходит те же элементы, что и при
подсчёте), поэтому не выходит за свой кусок. Каждая позиция выхода записывается ровно одним
потоком ровно один раз. Это подтверждено тестом `write_range_invariants`, который независимо
пересчитывает диапазоны по определению и сверяет их с состоянием рабочей области.

**Стабильность.** Блоки входа идут по порядку `0, 1, …`, куски выхода для одного значения —
в том же порядке, а внутри блока проход слева направо с растущим курсором сохраняет взаимный
порядок. Для «голых» `uint16_t` стабильность ненаблюдаема, но по конструкции алгоритм стабилен
и останется таким при добавлении полезной нагрузки.

**Повторное использование памяти.** После фазы 2 исходные счётчики `local[t][v]` не нужны:
на их месте лежат текущие позиции записи. Отдельная матрица `thread_offset[T][K]` не создаётся.

**Балансировка.** Фазы 1 и 3 — по `N/T` элементов на поток **при любом распределении данных**;
фаза 2 — по `K/T` значений на поток. Деление по диапазонам значений (поток 0 → значения
`0..16383`, …) катастрофически неравномерно при перекосе данных, поэтому не используется.

**Реальный размер команды.** Рантайм OpenMP вправе выдать меньше потоков, чем запрошено
(`OMP_THREAD_LIMIT`, вложенность и т. п.). Все разбиения считаются по
`omp_get_num_threads()` внутри области, а не по запрошенному числу — иначе часть блоков
осталась бы необработанной. Для `N < T` создаётся не более `N` потоков; `N = 0` — ничего не делает;
`--threads 1` — тот же алгоритм с одним блоком.

## 4. Почему локальные гистограммы, а не списки

Вариант «для каждого значения свой список индексов/указателей» невыгоден:

* индекс (4–8 байт) или указатель занимают **столько же или больше, чем сам элемент** (2 байта);
  для N = 10⁹ это дополнительные 4–8 ГБ (а у `std::list` — ещё 16–32 байта на узел), против 2 ГБ данных;
* на каждый элемент нужна аллокация или запись в динамическую структуру, обход списков —
  цепочки зависимых промахов кэша;
* списки по значениям всё равно придётся сливать и сопоставлять с потоками.

Локальные гистограммы занимают `T·K·4 байт` — **не зависят от N** (16 потоков → 4 МиБ), читаются
и пишутся только владельцем, обрабатываются подряд идущей памятью.

## 5. Почему в горячих циклах нет mutex / atomic / critical

Горячие циклы — фазы 1 и 3 (по N элементов). В фазе 1 поток пишет **только в свою** таблицу
(принцип *owner computes*). В фазе 3 поток читает свой блок входа, изменяет только свою строку
курсоров и пишет в позиции выхода, принадлежащие только ему (см. «Нет перекрытий»). Любая ячейка
памяти внутри фазы пишется не более чем одним потоком и не читается другими, то есть гонок данных
нет **по построению**. Единственная синхронизация — три `#pragma omp barrier` на весь алгоритм
(в OpenMP барьер неявно содержит `flush`, это даёт нужную видимость данных между фазами).
Общий атомарный счётчик `count[65536]` потребовал бы синхронизации на каждый элемент и заставил
бы кэш-линии с 16 соседними счётчиками «летать» между ядрами.

Выровненные по кэш-линии таблицы (`alignas(64)`) и границы диапазонов значений в фазе 2,
кратные размеру линии, исключают false sharing между потоками.

## 6. Сложность

| | Работа | Время на T ядрах |
|---|---|---|
| Последовательно | Θ(N + K) | Θ(N + K) |
| Параллельно | Θ(N + K + T·K) | Θ(N/T + K) |

Подсчёт и раскладка — `O(N)`; обнуление и слияние T гистограмм и префиксные суммы — `O(T·K)`,
не зависят от N и сами распараллелены (каждый поток слияет `T` таблиц на своих `K/T` значениях).
При `N ≫ T·K` слагаемое `T·K` пренебрежимо мало; при малых N (порядка `T·K` и меньше) параллельная
версия может быть **медленнее** последовательной — это свойство алгоритма, а не ошибка.

## 7. Оценка памяти

Формула: `M ≈ 2·N·sizeof(uint16_t) + T·K·sizeof(Count) + O(K)`, где `Count = uint32_t`.

| Компонент | Формула | N = 10⁹, T = 16 |
|---|---|---|
| Входной массив | N · 2 Б | 2 000 000 000 Б ≈ **1,86 ГиБ** |
| Выходной буфер | N · 2 Б | ≈ **1,86 ГиБ** |
| Локальные гистограммы | T · 65536 · 4 Б | 16·65536·4 = 4 194 304 Б = **4 МиБ** |
| Таблица стартов | (K + 16) · 4 Б | ≈ 256 КиБ |
| Суммы по диапазонам | T · 64 Б | 1 КиБ |
| **Итого** | | **≈ 3,73 ГиБ** |

Режимы `serial`, `parallel` и `benchmark` держат **ровно эти два массива** — отдельной копии «оригинала»
нет. Это возможно потому, что сортировка подсчётом читает вход и пишет в выходной буфер, **не изменяя
вход**; после `swap(data, buffer)` исходные данные целиком остаются в `buffer`, и «восстановление» входа
перед следующим запуском — это обмен указателями за O(1) (свойство закреплено тестом
`scatter_leaves_input_intact`, а то, что каждый запуск стартует с исходных данных, — тестом
`run_experiment_fairness_and_memory`).

Режим `fill` сортирует на месте и разрушает вход: при **единственном** запуске ему нужен 1 массив
(≈ 1,87 ГиБ при N = 10⁹), при нескольких запусках — 2 (вторая копия нужна, чтобы вернуть вход).

Гистограммы для других `T`: 8 потоков — 2 МиБ, 32 потока — **8 МиБ**, 64 потока — 16 МиБ
(при `-DRADIX_WIDE_COUNTERS=ON` вдвое больше).

Измеренный пиковый RSS на N = 10⁸ (один массив = 190,7 МиБ): `scatter` — 386–388 МиБ (2,0 массива в
режимах `serial` и `benchmark`), `fill` с одним запуском — 197 МиБ (1,03 массива), `fill` в `benchmark` —
388 МиБ. На N = 8·10⁸ (`scatter`, `benchmark`) — 3058 МиБ при двух массивах по 1526 МиБ. Скрытых
аллокаций, растущих с N, нет.

**Почему память критична.** Раскладка элементов — случайные записи по всему выходному массиву (65536
«потоков записи»). Пока массивы помещаются в ОЗУ, это секунды. Но если ОС начинает вытеснять страницы в
swap, каждая такая запись превращается в обращение к диску, и сортировка 10⁹ элементов занимает не секунды,
а часы. Поэтому перед выделением памяти программа сравнивает потребность с **доступной** ОЗУ
(`/proc/meminfo: MemAvailable` на Linux, `GlobalMemoryStatusEx` на Windows, `vm_stat` на macOS) и при нехватке завершается с
понятным сообщением (код 1); обойти проверку можно флагом `--force`.

## 8. Требования к системе

* компилятор с C++17 и **OpenMP** (проверено: GCC 13.3; код написан и под Clang с libomp и MSVC —
  только конструкции OpenMP 2.0, знаковые индексы, без `default(none)` — но на них не запускался);
* CMake ≥ 3.16 (необязательно: см. сборку одной командой);
* ОЗУ: для N = 10⁹ нужно около **3,73 ГиБ свободной** памяти в режиме `scatter` и около 1,87 ГиБ в
  `--algorithm fill` с единственным запуском (плюс память ОС и других программ);
* необязательно: Google Benchmark (для `radix_gbench`).

## 9. Сборка

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
ctest --test-dir build --output-on-failure      # тесты (быстрые, несколько секунд)
```

MSVC (Visual Studio): `cmake -S . -B build`, затем `cmake --build build --config Release` и
`ctest --test-dir build -C Release`; OpenMP подключается через `OpenMP::OpenMP_CXX` автоматически.
**macOS.** Apple Clang поставляется без OpenMP, поэтому сначала нужен libomp из Homebrew:

```bash
brew install libomp
rm -rf build                      # если конфигурация уже падала, удалите кэш
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j
```

`CMakeLists.txt` сам находит libomp (`brew --prefix libomp`, затем `/opt/homebrew/opt/libomp` и
`/usr/local/opt/libomp`) и подставляет нужные флаги. Если автоопределение не сработало, задайте их вручную:

```bash
LIBOMP="$(brew --prefix libomp)"
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
  -DOpenMP_CXX_FLAGS="-Xpreprocessor -fopenmp -I$LIBOMP/include" \
  -DOpenMP_CXX_LIB_NAMES=omp \
  -DOpenMP_omp_LIBRARY="$LIBOMP/lib/libomp.dylib"
```

Либо без CMake, одной командой:

```bash
clang++ -std=c++17 -O3 -Xpreprocessor -fopenmp -I"$(brew --prefix libomp)/include" \
  -L"$(brew --prefix libomp)/lib" -lomp -Isrc src/*.cpp -o sort_app
```

Эти шаги для macOS не проверялись в среде разработки (там Linux): это стандартный рецепт для Homebrew-libomp.

Опции CMake: `-DRADIX_WIDE_COUNTERS=ON` (64-битные счётчики для N > 4 294 967 295),
`-DRADIX_NATIVE_ARCH=ON` (`-march=native`), `-DRADIX_BUILD_TESTS=OFF`,
`-DRADIX_LARGE_TESTS=ON` (в CTest добавляется тест на 10⁸ элементов, ~400 МБ),
`-DENABLE_GOOGLE_BENCHMARK=ON` (необязательная цель `radix_gbench`; если библиотека не найдена,
выводится предупреждение, а основной проект собирается как обычно).

Без CMake, одной командой:

```bash
g++ -std=c++17 -O3 -fopenmp -Isrc src/*.cpp -o sort_app
```

## 10. Примеры запуска

```bash
./build/sort_app --help

# Сгенерировать тестовый файл (по числу на строку); суффиксы k/M/G — десятичные
./build/sort_app --mode generate --size 10M --output input.txt --seed 123 --distribution uniform

# Последовательная и параллельная сортировка файла с проверкой результата
./build/sort_app --mode serial   --input input.txt --verify
./build/sort_app --mode parallel --input input.txt --threads 8 --verify --output sorted.txt

# Бенчмарк на сгенерированных данных (без файлов)
./build/sort_app --mode benchmark --generate 100M --threads 16 --repeats 3
./build/sort_app --mode benchmark --generate 10M  --threads 1  --verify       # деградация до 1 потока

# Миллиард элементов (см. раздел «Очень большие массивы»)
./build/sort_app --mode generate --size 1G --output big.bin          # бинарный файл 2 ГБ (текстовый был бы ~6 ГБ)
./build/sort_app --mode parallel --input big.bin --threads 16 --verify
./build/sort_app --mode benchmark --generate 1G --threads 16         # для N >= 250 млн: 1 повтор, без прогрева
./build/sort_app --mode parallel --input big.bin --algorithm fill    # вдвое меньше памяти, существенно быстрее
```

Основные параметры: `--mode serial|parallel|benchmark|generate`, `--input FILE`, `--generate N`
(синоним `--size N`), `--distribution uniform|random|sorted|reverse|few-values|zeros|max|two-values`,
`--seed S`, `--threads T`, `--repeats R`, `--warmup` / `--no-warmup`, `--algorithm scatter|fill`,
`--format text|binary|auto` (по умолчанию `*.bin` — бинарный), `--verify`, `--output FILE`,
`--quiet` (без строк прогресса), `--force` (игнорировать предварительную проверку памяти), `--help`.
Значения по умолчанию: `--repeats 3` с одним прогревом, а при `N >= 250 000 000` — **один замер без прогрева**
(явные `--repeats` / `--warmup` имеют приоритет).
Коды возврата: `0` — успех, `1` — ошибка выполнения или провал проверки, `2` — неверные аргументы.

Распределения: `uniform` — равномерное; `random` — «колоколообразное» (среднее четырёх равномерных:
плотность неравномерна); `sorted` / `reverse` — лесенки; `few-values` — 16 различных значений;
`zeros`, `max`, `two-values` (только 0 и 65535) — крайние случаи. Генератор «счётчиковый»
(SplitMix64 по номеру элемента): данные зависят только от `seed` и размера, **не** от числа потоков и
компилятора, а файл на 10⁹ элементов пишется порциями без большого буфера.

## 11. Benchmark

Принципы честности (реализованы в `src/benchmark.cpp`):

* обе версии получают **одинаковые** исходные данные: перед каждым запуском массив приводится к
  исходному состоянию — для `scatter` это обмен `data`/`buffer` (вход сортировка не изменяет, лишней
  копии «оригинала» нет), для `fill` — копирование из эталонной копии. Тест
  `run_experiment_fairness_and_memory` проверяет, что КАЖДЫЙ запуск (прогрев, serial, parallel, все
  повторы) начинается ровно с исходных данных;
* восстановление, генерация, чтение/запись файлов и проверка **не входят** в время: замеряется только
  вызов сортировки (`std::chrono::steady_clock`); фазы дополнительно замеряются `omp_get_wtime()`;
* все буферы и `ParallelRadixWorkspace` выделяются **до** цикла замеров — аллокаций в измеряемом коде нет;
* один неучитываемый прогрев (запуск пула потоков, подкачка страниц, частота CPU), затем `--repeats R`
  повторов; `serial` и `parallel` чередуются в каждом повторе. По умолчанию — 3 повтора и прогрев, а при
  `N >= 250 000 000` — один замер без прогрева (4–8 запусков подряд на таком массиве выглядели бы как зависание);
* строки прогресса (`reading…`, `run 1/3: …`) печатаются в stderr только между замерами, отчёт — в stdout;
* `Speedup = T_serial / T_parallel` (по лучшему времени и по среднему),
  `Efficiency = Speedup / threads × 100 %`, где `threads` — **фактический** размер команды.
  При одном потоке отчёт добавляет пометку: отношение показывает накладные расходы параллельного алгоритма.

Рекомендации для серии измерений в курсовой (на многоядерной машине):

```bash
export OMP_PROC_BIND=close OMP_PLACES=cores        # закрепить потоки за ядрами
for t in 1 2 4 8 16 32; do
  ./build/sort_app --mode benchmark --generate 100M --threads $t --repeats 5 | grep -E "Threads:|Parallel:|Speedup:|Efficiency:"
done
# NUMA-серверы: numactl --interleave=all ./build/sort_app ...
```

Что ожидать. Раскладка (фаза 3) ограничена **памятью**, а не вычислениями: на каждый элемент приходится
случайная запись в один из 65536 потоков записи (на 4-КиБ страницах — ещё и промах TLB), поэтому
ускорение обычно заметно ниже линейного и упирается в пропускную способность памяти. Данные с
перекосом (отсортированные, `few-values`, `zeros`) замедляют фазу подсчёта: повторные инкременты
одного счётчика образуют цепочку зависимостей через память (в тестовой среде на 10⁸ элементов фаза
подсчёта занимала 0,22 с на `sorted` против 0,11 с на `uniform`). Зато у `sorted` раскладка `scatter`
почти не промахивается мимо кэша (0,11 с против 0,73 с на `uniform`).

### Расширение: режим `--algorithm fill`

Для ключей **без полезной нагрузки** отсортированный массив полностью определяется гистограммой:
`count[0]` нулей, `count[1]` единиц и т. д. После фаз 1–2 элементы не «раскладываются» по позициям,
а выходные диапазоны **заливаются**: фаза 3 — последовательная запись со скоростью памяти, без
случайных обращений и без второго массива. Параллелизм сохранён: фазы 1–2 те же; в фазе 3 каждый
поток заливает свой отрезок выхода в `N/T` элементов (начальное значение находит бинарный поиск по
таблице стартов), отрезки не пересекаются. Основной алгоритм по ТЗ — `scatter` — остаётся режимом
по умолчанию; `fill` включается явно.

Измерение в тестовой среде (последовательные версии, N = 10⁸, `uniform`, 1 ядро, `--repeats 3`):
`scatter` ≈ 0,85 с (подсчёт 0,12 с + раскладка 0,73 с), `fill` ≈ 0,14 с (подсчёт 0,11 с + заливка 0,03 с) —
примерно в 6 раз быстрее; основную долю `scatter` занимают случайные записи. При единственном запуске
`fill` держит один массив вместо двух (нет выходного буфера). Реальный прогон на N = 10⁹ (`uniform`,
`--mode serial --algorithm fill --verify`, 1 ядро): сортировка 1,37 с (подсчёт 1,09 с + заливка 0,28 с),
весь прогон вместе с генерацией и проверкой — 7,2 с, пик памяти 1912 МиБ. Это *не* заменяет стабильную
сортировку, если к ключу позже добавится полезная нагрузка: тогда нужен `scatter`.

## 12. Очень большие массивы (10⁸ – 10⁹ элементов)

Реальные прогоны в тестовой VM (1 ядро, 3,9 ГиБ ОЗУ, без swap; на вашей машине цифры будут другими,
соотношения сохранятся):

| Запуск | Время | Пик памяти |
|---|---|---|
| `--mode serial --algorithm fill --generate 1G --verify` (N = 10⁹) | сортировка 1,37 с; весь прогон 7,2 с | 1912 МиБ (1 массив) |
| `--mode benchmark --generate 800M --threads 4 --verify` (scatter: serial + parallel; ядро одно, поэтому ускорения нет) | serial 10,4 с, parallel 10,5 с; весь прогон 28,8 с | 3058 МиБ (2 массива) |
| `--mode parallel --input big500.txt --threads 4 --verify` (текст 2,72 ГиБ, N = 5·10⁸) | чтение 3,7 с, сортировка 6,0 с | 1914 МиБ (2 массива) |

Стоимость раскладки `scatter` растёт с N: 8,5 нс на элемент при 10⁸, 11,5 нс при 5·10⁸ и 13 нс при
8·10⁸ (случайные записи всё хуже попадают в кэш и TLB). На N = 10⁹ в такой VM следует ожидать порядка
13–14 с на одну сортировку (это экстраполяция, не измерение: полный `scatter` на 10⁹ не помещается в
память песочницы, требуется ≈ 3,73 ГиБ свободной ОЗУ).

Как не ждать «вечность»:

1. **Следите за прогрессом.** Строки в stderr (`[ 12.3 s] reading: 1.4 GiB of 5.5 GiB (25%), 720 MiB/s…`,
   `run 1/1: serial sort of … keys...`) показывают, на какой стадии программа. Если строки идут — она работает.
2. **Хватит ли памяти.** Для `scatter` нужно ≈ 3,73 ГиБ свободной ОЗУ на N = 10⁹ (два массива). Если
   памяти меньше, ОС уйдёт в swap, и сортировка растянется на часы, поэтому программа заранее отказывается
   стартовать и пишет, сколько нужно и сколько есть (`--force` отключает отказ). Освободите память или
   возьмите `--algorithm fill` (≈ 1,87 ГиБ, один массив).
3. **Бинарный файл вместо текстового.** Для 10⁹ ключей текст занимает ≈ 6 ГБ и читается минутами,
   бинарный (`--format binary` или расширение `.bin`) — 2 ГБ и читается на скорости диска.
4. **Один замер по умолчанию.** Для `N >= 250 000 000` выполняется одна сортировка без прогрева. Усреднение
   включается явно (`--repeats 3 --warmup`), но время вырастет кратно.
5. **`--threads`** не превышайте числа физических ядер; на многосокетных серверах — `numactl --interleave=all`.

## 13. Ограничения

* `N ≤ 4 294 967 295` при 32-битных счётчиках (с запасом покрывает 10⁹); для большего — `-DRADIX_WIDE_COUNTERS=ON`.
  Превышение размера диагностируется сразу (до генерации и чтения данных), а не молчаливым переполнением.
* `T ≤ 1024`; память гистограмм линейна по `T` (`T·256 КиБ`).
* При малых `N` (порядка `T·65536` и меньше) накладные расходы `O(T·K)` и false sharing на границах
  выходных диапазонов (когда на пару «поток, значение» приходится всего несколько элементов) могут
  свести ускорение к нулю — параллельная версия намеренно не подменяется последовательной,
  чтобы эффект был виден в экспериментах.
* Текстовый ввод принимает только беззнаковые десятичные целые `0..65535`, разделённые пробельными
  символами (допустимы CRLF, пустые строки, BOM); любая другая лексема — ошибка с номером строки.
* NUMA: массивы создаются главным потоком; на многосокетных машинах используйте
  `numactl --interleave=all` или `OMP_PROC_BIND`/`OMP_PLACES`. Прозрачные большие страницы (THP):
  в тестовой VM `madvise(MADV_HUGEPAGE)` на выходной буфер не ускорил, а замедлил раскладку
  (1,6 → 2,4 с на N = 2·10⁸), поэтому программа их не использует; на вашей системе результат может быть другим.
* Предварительная проверка памяти — оценка: она учитывает массивы, таблицы гистограмм и данные проверки, но
  не знает о потребностях других программ; на macOS свободная память берётся из вывода `vm_stat`
  (free + inactive + speculative + purgeable); если его не удалось разобрать, сравнение идёт с общим объёмом ОЗУ.
  `--force` отключает отказ.
* Из-за `swap` векторов по возвращении `buffer` содержит старый вход, а указатели на `data.data()`
  меняются местами с `buffer.data()`.
* Один `ParallelRadixWorkspace` — один одновременный вызов сортировки.

## 14. Что и где проверено

Окружение разработки: Linux x86-64, GCC 13.3, **1 виртуальное ядро**, 3,9 ГиБ ОЗУ (swap нет).

* Сборка с `-Wall -Wextra -Wpedantic -Wshadow -Wconversion -Wsign-conversion` — без предупреждений.
* `radix_tests`: **21 группа, 8592 проверки, 0 ошибок** — обычная сборка, ASan+UBSan, 64-битные счётчики,
  `--large` (10⁸ элементов), а также при `OMP_THREAD_LIMIT=2/3`, `OMP_DYNAMIC=true`,
  `OMP_WAIT_POLICY=active/passive` (ветка «команда меньше запрошенной»). Покрыто: `N = 0, 1, 2, N < T,
  N = T, N > T`; все 0; все 65535; одно/два значения; sorted; reverse; random — для `T ∈ {1,2,3,4,7,8,16,33,64}`;
  размеры 10³, 10⁴, 10⁶, 10⁷, 10⁸; повторное использование рабочей области с меняющимися `N` и `T`;
  инварианты диапазонов записи; ввод-вывод (включая число, разрезанное границей блока чтения и границу
  порций бинарного чтения); генератор; модуль проверки; **scatter не изменяет вход**; **каждый запуск
  бенчмарка стартует с исходных данных**; оценка памяти; настройки по умолчанию; оценка числа ключей в файле.
* Тест честности проверен **мутациями**: если намеренно сломать восстановление входа (для `scatter` или для
  `fill`), он падает. Без него сломанный бенчмарк тихо сортировал бы уже отсортированные данные и проходил бы
  все проверки корректности.
* Большие прогоны (см. раздел 12): N = 10⁹ в режиме `fill` целиком, с проверкой; N = 8·10⁸ в режиме
  `scatter` (serial + parallel) с проверкой; текстовый файл N = 5·10⁸ (2,72 ГиБ) с чтением, прогрессом и проверкой.
* Предварительная проверка памяти: на 1,5·10⁹ в `scatter` (нужно 5,59 ГиБ при 3,69 ГиБ доступных) программа
  отказывается мгновенно с понятным сообщением; N > 4 294 967 295 отвергается до генерации данных.
* Результат `--output` побайтово совпал с `sort -n` из coreutils.
* **Не проверено** (в среде нет): ускорение на многоядерной машине; полный `scatter` на 10⁹ (не хватает памяти
  в песочнице, проверен масштаб 8·10⁸); сборка Clang и MSVC; macOS; ветки `_WIN32` и `__APPLE__` в
  `sysinfo.cpp` (макОС-ветка проверена только компиляцией на заглушке системного заголовка; разбор `vm_stat` — тестом); конфигурирование через CMake (файл `CMakeLists.txt` проверен чтением,
  команды тестов воспроизведены вручную); цель `radix_gbench` с настоящей Google Benchmark (проверена только
  компиляция на заглушке API). Запустите `ctest` у себя — это дело нескольких секунд.
